# ZooidManager 多机器人同步测试模式设计

日期：2026-08-30

## 1. 目标

以现有 `ZooidManager` 为唯一底层通信和机器人管理框架，增加一个可从界面启动的“测试模式”，通过同一个 USB 接收器体系向所有当前在线且已激活的 e-puck2 机器人同步发送左右轮速度命令。

本阶段只验证完整硬件链路：界面按钮、在线机器人识别、机器人 ID 路由、串口组帧、速度发送、状态反馈和安全停止。暂不移植追逐算法，也不启用 Voronoi、Follow、Triangle、Charge 等现有控制模式。

## 2. 非目标

- 不在本阶段引入 ROS 运行时或 ROS 节点。
- 不删除现有模式的底层源文件和管理器接口，以便后续参考或恢复。
- 不修改接收器固件和机器人固件协议。
- 不让测试过程中才上线的机器人自动加入本轮测试。
- 不连续循环测试动作；每次点击只执行一轮。

## 3. 用户界面

首页控制区仅向用户提供两个可操作按钮：

- `开始测试`：在存在至少一台在线且已激活机器人时启动一轮测试。
- `停止`：无论测试当前处于哪个阶段，都立即终止状态机并向本轮目标机器人发送零速。

原有模式按钮不再显示，也不连接到可操作入口；相关模式实现源码保留。测试运行期间重复点击 `开始测试` 不会重启或叠加新一轮测试。若没有可用机器人，则拒绝启动，并在界面状态区显示原因。

界面通过管理器的只读运行状态更新按钮可用性和提示文字，不直接操作串口。

## 4. 固定测试序列

左右轮速度沿用 ZooidManager 当前速度单位和范围，满速为 `+/-1000`。本测试使用保守速度：

| 阶段 | 左轮 | 右轮 | 持续时间 |
|---|---:|---:|---:|
| 前进 | +200 | +200 | 2 秒 |
| 停止 | 0 | 0 | 1 秒 |
| 左转 | -150 | +150 | 2 秒 |
| 停止 | 0 | 0 | 1 秒 |
| 右转 | +150 | -150 | 2 秒 |
| 停止 | 0 | 0 | 1 秒 |
| 后退 | -200 | -200 | 2 秒 |
| 最终停止 | 0 | 0 | 至少 3 个连续发送周期 |

状态机只执行一轮，完成最终停止后回到空闲状态。

## 5. 架构

新增一个不依赖 Qt、串口和机器人对象的纯 C++14 状态机 `ZooidTestMode`。它只负责根据单调时间生成左右轮速度，不负责查找机器人、编码协议帧或写串口。

建议的数据类型和接口如下：

```cpp
struct WheelCommand {
    int16_t left;
    int16_t right;
};

struct TestModeOutput {
    WheelCommand wheels;
    bool running;
    bool completed;
};

class ZooidTestMode {
public:
    bool start(uint64_t nowMs);
    void stop();
    bool isRunning() const;
    TestModeOutput update(uint64_t nowMs);
};
```

`ZooidManager` 拥有该状态机，并承担以下职责：

1. 启动时生成目标机器人 ID 快照。
2. 每个管理周期处理接收器反馈和机器人在线状态。
3. 以约 60 Hz 调用状态机并把同一组轮速发送给全部有效目标 ID。
4. 负责串口组帧、接收器选择、局部 ID 映射和缓冲区刷新。
5. 处理停止、完成、掉线、串口异常和程序退出。

`HomePage` 只调用 `ZooidManager::startTestMode()`、`ZooidManager::stopTestMode()` 并显示状态。

## 6. 时间模型

测试阶段计时使用 `std::chrono::steady_clock`，不使用系统墙钟，也不使用现有的 `clock()` CPU 时间。管理器把从单调时钟得到的毫秒值传给状态机，使计时不受系统时间调整影响，并可在单元测试中注入任意时间点。

若一个管理周期因系统负载跨过多个阶段边界，状态机应基于总经过时间直接定位到正确阶段，不能把每个阶段重新从当前时刻开始，否则会使整轮测试越跑越慢。

## 7. 目标机器人与 ID 路由

点击 `开始测试` 时，在 ZooidManager 的机器人集合锁保护下，保存所有 `connected && activated` 机器人的全局 ID，形成不可扩张的本轮目标快照。

发送时继续复用 ZooidManager 已有路由规则：

- 接收器编号：`globalId / 10`
- 接收器内局部 ID：`globalId % 10`

本轮开始后新上线的机器人不加入目标快照。目标机器人若掉线、超时或被停用，则立即从本轮有效发送集合排除，并向仍可通信的接收器补发该机器人的零速帧。其他在线目标继续完成测试；若所有目标都不可用，则整轮测试安全停止。

机器人反馈仍由现有 `TYPE_STATUS` 接收路径解析并存储在对应的 `Zooid` 对象中，测试模式不建立第二套 ID 或反馈存储结构。

## 8. 串口速度帧

继续调用现有 `controlRobotSpeed(globalId, left, right)` 路径。USB 外层帧保持：

```text
0x7E | TYPE_ROBOT_POSITION | localRobotId | payloadLength | payload | 0x21
```

速度使用当前固件约定写入 `PositionControlMessage`：

```text
positionX = leftWheelSpeed  + 2000 + 7
positionY = rightWheelSpeed + 2000 + 7
orientation = 52000
```

例如 `(+200, +200)` 对应两个字段均为 `2207`，`(-150, +150)` 对应 `1857` 和 `2157`，零速对应 `2007`。

构造 `PositionControlMessage` 时必须先整体零初始化，再显式设置所有当前协议要求字段，特别是 `controlMode`，防止未初始化字节随机进入串口负载。颜色、`preferredSpeed`、`isFinalGoal` 和 `empty` 继续遵循当前 ZooidManager 固件兼容值。

速度值在编码前钳制到 `[-1000, +1000]`，即使将来上层算法输出越界也不能把非法速度写入协议帧。

## 9. 管理循环集成

管理线程始终先执行接收器数据处理和在线状态维护。测试模式激活时进入独占控制分支：

1. 更新本轮目标机器人的有效性。
2. 从 `ZooidTestMode` 获取当前轮速。
3. 向全部有效目标发送相同轮速。
4. 刷新涉及的接收器输出缓冲区。
5. 跳过 `assignRobots()`、`runSimulation()`、`sendRobotsOrders()` 和其他旧模式控制输出。

测试未运行时，本阶段也不自动进入旧模式控制。在线登记、状态反馈、位置数据更新等共享基础功能继续运行；Charge、Voronoi 等与测试无关的周期更新在测试入口版界面中不触发。

为保持现有 `addZooid()` 依赖关系稳定，模拟器、目标、充电和跟随相关对象的基础初始化暂时保留，但它们不获得控制权，也不向机器人发动作命令。

## 10. 并发与状态同步

Qt 界面线程和 ZooidManager 管理线程可能同时访问测试状态。测试运行标志、停止请求和目标 ID 集合必须使用现有互斥机制或专用互斥量保护，不能依赖普通 `bool` 的未同步读写。

界面发出的停止请求优先于下一条非零速度命令。管理循环观察到停止后不得再从旧阶段发送非零速度。串口发送仍使用现有 `ZooidReceiver` 的线程安全输出队列。

## 11. 安全停止与异常处理

所有停止路径最终收敛到同一个管理器方法，避免某条路径只改状态、不发零速：

- 用户点击 `停止`。
- 固定序列自然结束。
- 本轮所有目标掉线或失活。
- 接收器写入失败或接收器停止工作。
- 窗口关闭或程序退出。

停止动作包含：

1. 原子地禁止新的非零测试命令。
2. 对仍可路由的本轮目标排队发送零速。
3. 立即刷新相关接收器。
4. 在连续 3 个管理周期重复零速，以降低单帧丢失风险。
5. 清空本轮目标和阶段状态，返回空闲。

若部分机器人掉线，系统不能假称已成功停住该机器人；界面应显示掉线 ID，操作者需要物理确认。程序退出顺序必须是先完成可发送的零速批次，再关闭接收器线程和串口。

## 12. 测试策略

实现遵循测试驱动顺序，先建立失败测试，再实现最小代码。

### 12.1 纯状态机单元测试

- 启动时输出前进速度。
- `1999 ms` 仍前进，`2000 ms` 进入第一次停止。
- 每个阶段边界的速度和持续时间准确。
- 大时间步可跨越多个阶段并落在正确阶段。
- 完整序列只运行一次并报告完成。
- 运行中再次启动被拒绝。
- 任意阶段手动停止后输出零速且不再恢复非零命令。

### 12.2 编码和限幅测试

- `+200` 编码为 `2207`。
- `-150` 编码为 `1857`。
- `0` 编码为 `2007`。
- 超过 `+1000/-1000` 的值被钳制。
- 负载对象零初始化，协议字段值确定。

### 12.3 管理器集成检查

使用可替换或记录型发送接口验证：

- 启动时只快照在线且激活的 ID。
- 多台机器人收到相同阶段命令但各自使用正确接收器和局部 ID。
- 后上线机器人不加入当前轮次。
- 掉线机器人被排除，其余机器人继续。
- 停止、完成和退出均产生零速帧并刷新接收器。
- 测试运行时不会调用旧模式订单发送路径。

### 12.4 实机验收

先架空轮子或将机器人放在有足够安全空间的场地，按以下顺序验收：

1. 单台机器人确认前进、左右转和后退方向。
2. 两台机器人确认同步动作和独立 ID 路由。
3. 全部机器人确认同步动作。
4. 每个非零阶段点击停止，确认均立即归零。
5. 测试中断开一台机器人，确认其他机器人行为和界面告警。

## 13. 预计修改范围

- 新增 `manager/ZooidTestMode.h/.cpp`：纯状态机。
- 新增状态机及协议编码测试文件和独立测试构建入口。
- 修改 `ZooidManager.pro`：加入新源文件。
- 修改 `manager/ZooidManager.h/.cpp`：公开测试控制接口、目标快照、独占发送分支、安全停止和退出处理。
- 修改 `manager/ZooidReceiver.h/.cpp`：仅在验证确有需要时补充可观测的写失败状态或显式刷新接口。
- 修改 `mainWindow/homePage.h/.cpp`：只显示开始测试和停止入口，展示运行/失败状态。

不删除 Voronoi、Follow、Charge、Triangle 等现有模式源码。

## 14. 后续算法移植接口

测试模式验证通过后，`epuck-pursuit-webots` 的追逐算法只需替换“轮速产生器”：算法根据 ZooidManager 已存储的各机器人位置、朝向和 ID 计算每台机器人的左右轮速度，随后复用本设计的限幅、路由、串口编码、反馈、掉线处理和安全停止链路。

因此第一阶段不把固定序列写死在串口层，也不让界面直接组帧；这两个边界保证后续移植不需要再次改造底层通信。

## 15. 验收标准

- 首页仅有清晰的开始测试和停止操作入口。
- 无在线机器人时不能启动。
- 所有启动时在线且已激活的机器人按固定序列同步运动一轮。
- 串口速度字段与现有 `+2007` 偏置协议一致，速度限制为 `[-1000, +1000]`。
- 每台机器人按全局 ID 正确映射到接收器和局部 ID。
- 反馈继续更新到对应 Zooid 对象。
- 手动停止、自然完成、通信异常和程序退出均执行安全零速。
- 测试运行期间没有旧模式控制命令与测试命令竞争。
- 自动化测试覆盖状态机边界、编码、目标快照和停止路径。
